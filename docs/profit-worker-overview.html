Profit Worker
운영 해부도

실제 Java 코드 기준으로 정리한 Finvibe profit worker 문서다. 이 서비스는 Kafka 배치 이벤트를 받아 Redis 운영 상태를 갱신하고, 포트폴리오·유저 valuation snapshot을 dirty set으로 staging하는 수익률 계산 워커다.

3Kafka topic ingress
7주가 재계산 단계
2valuation aggregate 축
10+Redis key family
Kafka Batch Ingress

StockPriceEventConsumer, CacheUpdateEventConsumer가 List<String> payload를 수신한다.

Application Ports

Use case는 Redis adapter를 직접 알지 않고 PortfolioStateStore, UserStateStore, ValuationRepository 포트로 통신한다.

Redis Operational State

역인덱스, 포트폴리오 hash, 보유종목 leaf key, 유저 hash/set이 계산의 working set이다.

Dirty Snapshot Staging

valuation hash를 갱신한 뒤 dirty:* set에 ID를 넣어 후속 write-back 대상임을 표시한다.

2. 이벤트 입력 계층

batch normalization

Kafka listener 설정은 batch mode이며 기본 concurrency는 3, max poll records는 50이다. Consumer는 JSON 문자열 목록을 DTO로 역직렬화하고, use case request로 변환한다.

정수 가격만 허용

BUY/SELL만 지원

거래 이벤트 amount는 양수여야 하며, type은 STOCK_BUY 또는 STOCK_SELL로 변환된다.

3. 가격 업데이트 이벤트가 도착했을 때

7-stage fanout

주가 변경은 “전체 포트폴리오 재계산”이 아니다. 변경된 종목을 가진 포트폴리오만 찾고, 기존 종목별 평가액과 신규 평가액의 delta만 aggregate hash에 누적한다.

01 / consume

Kafka batch 수신

StockPriceEventConsumer.consumeStockPriceUpdatedEvents가 payload 목록을 받는다.

  • Timer 시작
  • JSON → StockPriceUpdatedEvent
02 / dedupe

stockId 기준 최신값 압축

LinkedHashMap에 stockId를 key로 넣어 같은 배치의 중복 종목을 제거한다.

  • batch size / deduplicated size 기록
  • event age 기록
03 / reverse index

영향 포트폴리오 조회

stock:{stockId}:portfolios set을 pipeline SMEMBERS로 읽는다.

  • stockId → portfolioIds
  • 작업 task 생성
04 / prefetch

보유 수량·기존 평가액 조회

각 portfolio-stock 조합에 대해 quantity와 stock current-value를 pipeline GET한다.

  • portfolio:{id}:stock:{stockId}:quantity
  • ...:current-value
05 / delta

메모리에서 delta 계산

newPrice * quantity - oldStockCurrentValue를 계산하고 portfolio별 delta를 합산한다.

  • Redis 호출 없음
  • quantity 0은 skip
06 / aggregate update

포트폴리오 aggregate 반영

pf:{portfolioId}의 cvp에 delta를 pipeline HINCRBYFLOAT로 누적하고 metadata를 HMGET한다.

  • portfolio valuation build
  • stock current-value SET
07 / snapshot save

포트폴리오 snapshot 저장

계산된 portfolio valuation을 저장하고 dirty set과 가격 재계산 메트릭을 갱신한다.

  • bulkSavePortfolioPriceUpdateValuations(...)
  • affected portfolio 기록

state maintenance

7. 성능 개선 포인트

ranked backlog

현재 코드는 이미 주가 fanout에서 batch·dedupe·Redis pipeline·delta update 전략을 사용한다. 다음 개선안은 실제 코드에서 관찰된 병목 후보와 안정성 리스크를 기준으로 우선순위를 매겼다.

우선순위개선 포인트현재 코드 근거기대 효과 / 주의점
P1금융 금액 누적에서 double 기반 HINCRBYFLOAT 제거 또는 fixed-point 전략 도입RedisPortfolioStateStore, RedisUserStateStore가 BigDecimal delta를 doubleValue()로 변환해 cvp에 누적한다.장기 누적 오차 리스크를 줄인다. 원 단위 정수면 scaled long HINCRBY, 소수 수량까지 보존해야 하면 정해진 scale의 fixed-point 또는 Lua 기반 decimal string 갱신을 검토한다.
P1거래 이벤트 캐시 갱신도 pipeline/bulk화CacheUpdateService.updatePortfolioCaches는 batch를 받지만 각 request마다 quantity 조회/쓰기, set add/remove, hash increment를 개별 호출한다.거래 폭주 시 Redis round-trip을 크게 줄인다. 단, BUY/SELL 순서가 의미를 가지므로 같은 portfolio-stock 내 이벤트 순서를 보존하거나 batch 내 netting 규칙을 명확히 해야 한다.
P1주가 dedupe 기준을 “배치 순서”가 아니라 event timestamp/offset 정책으로 명확화LinkedHashMap.put(stockId,event)는 동일 batch 안에서 나중에 순회된 payload가 최신이라고 가정한다.Kafka partition/order 보장이 stockId 단위로 맞지 않거나 재시도·재배치가 섞이면 오래된 가격이 최신 가격을 덮을 수 있다. key를 stockId로 partition하거나 updatedAt 비교 정책을 명시한다.
P2주가 fanout의 task cardinality 상한과 chunking 적용한 stockId가 매우 많은 포트폴리오를 가지면 tasks, stockHoldings, valuation list가 메모리에 한 번에 만들어진다.대형 종목 fanout에서 heap spike와 Redis pipeline payload 폭증을 막는다. stockId 또는 portfolio task를 일정 크기로 chunking하고 phase metric에 chunk index/size를 남긴다.
P2dirty set write-back consumer 또는 운영 계약 문서화RedisValuationRepositoryAdapter는 dirty set에 쓰지만 이 repository에서 dirty set을 읽어 DB에 반영하는 active code는 확인되지 않는다.Redis snapshot이 최종 저장소가 아니라면 write-back lag/누락이 장애가 된다. 별도 서비스가 담당한다면 SLA와 key contract를 명확히 해야 한다.
P2포트폴리오 hash writer 충돌 정리pf:{id}는 state store가 cvp/pv/ac/u를 갱신하고 valuation adapter가 cv/pr/ua/del을 갱신한다.동일 hash에 운영 상태와 snapshot 필드가 섞여 있어 장애 분석이 어렵다. key 분리 또는 field ownership table을 강제하면 유지보수성이 좋아진다.
P3미사용 profitRecalculationExecutor 정리 또는 실제 사용ProfitRecalculationExecutorConfig bean은 존재하지만 main code에서 참조가 확인되지 않는다.사용하지 않는 병렬 설정은 운영자가 실제 처리량에 영향을 준다고 오해할 수 있다. 삭제하거나, fanout chunk 병렬화에 연결할 때 backpressure 정책까지 함께 설계한다.
P3Monolith HTTP client 역할 재검토MonolithHttpClient와 MonolithClient port는 존재하지만 main application service에서 참조되지 않는다.초기 cache bootstrap 용도라면 bootstrap path를 명시하고, 더 이상 쓰지 않는다면 삭제해 아키텍처를 단순화한다.
가장 먼저 볼 병목: Prometheus에서 profit.worker.phase.duration{phase="reverse_index_lookup"}, pipeline_get_stock_holdings, pipeline_hincrbyfloat_hmget_portfolio, pipeline_save_*_price_updates를 함께 보면 가격 이벤트 fanout의 병목이 조회·계산·쓰기 중 어디인지 분리된다.
